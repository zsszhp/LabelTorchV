## 1. 目标与非目标

### 1.1 目标

打通「上一版模型 → 辅助标注 → 增量训练 → 对比验收 → 晋级」的数据闭环，让数据闭环在产品内真转起来：

1. **增量训练产品化**：从模型中心选 `last.pt` / `best.pt` 一键续训或微调，配套增量数据快照与新旧 run 曲线叠加对比。
2. **主动学习闭环 UI**：难例挖掘页接真实 `active_learning_items` 数据，低置信 / 漏检 / 误检三队列可用，一键送标注并回写。
3. **错误分析报告**：逐类漏检超检排行、混淆矩阵可交互、失败案例可视化，一键导出自包含 HTML 报告。
4. **模型版本治理**：`production` 标签唯一、晋级 / 回滚语义化、精度回归告警。

### 1.2 非目标（本期明确不做）

1. 新增模型家族（SAM、RT-DETR 等）与新任务类型。
2. 主动学习采样策略升级（不确定性采样、委员会投票等），本期只做「队列产品闭环」。
3. 分布式 / 多机训练、云端同步、多人协作。
4. 报告的 PDF 排版引擎（本期交付自包含 HTML，PDF 由浏览器打印导出）。
5. 视频流主动学习、产线在线闭环。
6. 浅色主题、多语言界面。

## 4. 任务分解（A~D 实施级）

工作量单位为人日。编号：主任务字母 + 子任务序号。总工作量约 25 人日。

### 4.1 主任务 A：增量训练产品化

#### A1 续训 / 微调一键入口（3 人日）

**现状**：`TrainingService::createRun` 写 `config_snapshot_json`；Python 适配器 `ultralytics_adapter.py:61-158` 已实现 resume 断点定位与无断点报错，但产品层没有选版本入口，config 里也没有来源血缘字段。

**目标**：从模型中心选版本一键续训（last.pt）或微调（best.pt）；血缘可溯到 source_model_version_id 与 parent_run_id；权重不存在 / 跨项目路径被拒。

**逐步实现**：

1. **config_snapshot_json 扩展**（TrainingService.cpp createRun 写入，字段字典见附录 A）：
   - `resume_from`：权重绝对路径（仅项目内白名单路径）。
   - `resume_mode`：`"resume"`（续训）或 `"finetune"`（微调）。
   - `source_model_version_id`、`parent_run_id`：来源血缘。
2. **产品语义**（必须写进 ConfigPanel 帮助文案）：
   - 选 `last.pt` → `resume_mode=resume`，config 带 `resume:true` + `resume_weight`，适配器走 `ultralytics_adapter.py:154-158` 既有断点路径，epoch/优化器状态接续；无断点时报「无断点权重，无法增量训练」。
   - 选 `best.pt` → `resume_mode=finetune`，`resume:false`，权重通过 `model=best.pt` 冷启动加载；UI 预填更小学习率（lr0=0.001）与更少 epoch（默认 50），均可改。
3. **路径白名单**：`TrainingService` 写库前校验 `resume_from` 必须位于 `ProjectFs::modelsDir` 或 `versionsDir` 之下（`ProjectFs.cpp:104/109`），拒绝跨项目与不存在路径，错误文案含实际路径与允许范围。
4. **IPC 载荷**：`train.start` payload 增加 `resume_from/resume_mode`，后端 training.py 透传进 adapter config（Python 侧 key 已兼容 `resume_weight`，做一次键名映射即可）。
5. **注册血缘**：新 run 产出模型版本时 `ModelRegistry::registerModelVersion` 后调 `setParentVersion(newId, source_model_version_id)`（`ModelRegistry.h:43`），增量链进父子图。
6. **UI**：TrainingPage 增「从上一版继续训练」按钮 → 弹窗按项目列 model_versions（标签 + mAP 摘要，走 `listModelVersions`）→ 选中自动带出权重路径与建议超参（续训不预填 lr）。

**测试用例**：
- T1-1 选 last.pt 续训出新 run，epoch 从断点接续（run_metrics 首 epoch 大于 1），日志连续。
- T1-2 无 last.pt 时 resume 启动失败且错误信息含「无断点权重」（扩展 `backend/tests/test_resume_and_config.py`）。
- T1-3 选 best.pt 微调出独立新 run，config_snapshot_json 可查 source_model_version_id / parent_run_id。
- T1-4 权重不存在 / 项目外路径被拒，createRun 返回错误码 `E_WEIGHT_PATH`。

**验收命令**：

```powershell
cmake --preset msvc2022-release; cmake --build --preset msvc2022-release
ctest --preset msvc2022-release -R "TrainingTest|ModelTest" --output-on-failure
cd backend; python -m pytest tests/test_resume_and_config.py -q; python -m ruff check .
# GPU 机手工：last.pt 续训 10→11 epoch、best.pt 微调 50 epoch 各跑通一次
```

**常见坑**：
- Ultralytics 的 `resume=True` 与 `model=xxx.pt` 不能混用语义：续训只传 resume 断点，微调只传 model 权重，两路径在适配器里分支，别都塞。
- `source_model_version_id` 必须在 createRun 时落库而非训练结束才写——中途崩溃的 run 也要有血缘。
- 跨项目路径校验要规范化 `QDir::cleanPath` 后再比较，防 `../` 逃逸。

#### A2 增量数据快照（3 人日）

**现状**：`SnapshotService::createSnapshot`（SnapshotService.h:37）全量入册并哈希冻结（SnapshotService.cpp:213-238）；manifest 插入 `:279`。无增量模式。

**目标**：新增样本全量入册 + 历史样本按类分层采样（默认 30%，可配）；manifest 记录 `base_snapshot_id` 与采样策略；同参数可复现；哈希冻结不放松。

**逐步实现**：

1. `SnapshotService` 新增 `Q_INVOKABLE QString createIncrementalSnapshot(datasetId, trainRatio, baseSnapshotId, sampleRatio, seed)`；内部复用既有收集/哈希逻辑，差别只在样本集合选取。
2. **可复现采样**（附录 B 字段）：历史样本（base 快照成员）按 `hash(sampleId + seed) % 1000 < sampleRatio*1000` 决定取舍，按类分层保证每类比例；禁止用随机数发生器，否则两次创建不可复现。
3. manifest 扩展字段：`base_snapshot_id`、`sample_mode:"incremental"`、`sample_ratio`、`seed`、每条 entry 增 `source:"new"|"sampled"`；全量模式保持原格式（新字段只出现在增量模式，兼容读取见 SnapshotService getSampleManifest）。
4. 训练前漂移校验（E_SOURCE_DRIFT）不放松：prepareSnapshotPhysicalDir 既有校验链路直接生效。
5. SnapshotPage.qml：快照预览区分「新增 / 采样」标记与来源过滤；增量创建表单加 base 快照选择与比例滑条。

**测试用例**：
- T3-1 同数据集同参数两次增量快照，manifest 样本集合完全一致（可复现）。
- T3-2 冻结后篡改样本图，续训前校验报 E_SOURCE_DRIFT。
- T3-3 分层采样后每类占比与设定比例误差 ≤ 2 个百分点。
- T3-4 全量快照行为不回归（既有 ctest 全绿）。

**验收命令**：`ctest --preset msvc2022-release -R "SnapshotTest|SnapshotHashTest" --output-on-failure`

**常见坑**：
- 采样基于 sampleId 哈希而非行序，否则数据库返回顺序变化会导致不可复现。
- 增量快照的 split 划分要沿用 base 快照对历史样本的 split（历史样本不得重新划分，否则曲线不可比），只有新增样本参与新划分——这条写进测试。
- manifest 兼容：读取端必须同时接受旧格式（纯 id 数组）与新格式（对象数组），参照 SnapshotService::parseManifestHashes。

#### A3 新旧训练曲线对比（2 人日）

**现状**：`MetricService::getMetricHistory`（MetricService.h:26）与 `getRunMetrics`（:78）可用；ComparePage / MetricChart 已有组件；无多 run 叠加。

**目标**：任选两个 run 叠加 epoch 曲线（mAP50、mAP50-95、box/cls/dfl loss 多轴切换）；对比卡显示最终指标差值（涨跌着色：绿 / 黄 / 红）与耗时、样本量、快照来源；续训 run 可一键跳父 run。

**逐步实现**：

1. `MetricService` 新增 `Q_INVOKABLE QVariantList getRunCurves(QVariantList runIds, QVariantList metricNames)`：按 run_id+metric_name 查 run_metrics（走 idx_run_metrics_run），按 epoch 对齐返回；无数据 run 返回空序列由 UI 出 EmptyState。
2. ComparePage 叠加模式：曲线多色、图例 run 短 id；差值卡 = 两 run 最终值之差（含单位），阈值：退化 >2pp 红、涨跌 ≤0.5pp 灰、否则绿。
3. 血缘跳转：config_snapshot_json.parent_run_id 非空时显示「查看父 run」按钮。
4. 数据导出 CSV（可选小项）：走 writeFileAtomically 落 `{project}/logs/`。

**测试用例**：T5-1 双 run 叠加值与 run_metrics 直查逐点一致；T5-2 差值计算正确且着色分档正确；T5-3 空 run 空态。

**验收命令**：`ctest --preset msvc2022-release -R "ModelTest|TrainingTest" --output-on-failure`

**常见坑**：metric_name 拼写按 Ultralytics 实际落库值（含 `(B)` 后缀），先 `SELECT DISTINCT metric_name FROM run_metrics` 确认；两 run 的 epoch 集合不同时按并集对齐、缺失点断线不补零。

### 4.2 主任务 B：主动学习闭环 UI

#### B1 难例队列页接真实数据（3 人日）

#### B2 一键送标注 → 确认 → 回写（3.5 人日）

#### D1 production 唯一性与晋级 / 回滚（2.5 人日）

**现状**：`ModelRegistry::setTag`（ModelRegistry.cpp:234-283）只是把 tag 追加进 `metrics_snapshot_json.tags` 数组——同项目可以有多个 production，无事务、无审计；`removeTag`（:285）同样单行操作。这是本期最大的正确性缺口。

**逐步实现**：

1. **setTag 事务化**（`ModelRegistry.cpp` 重写 setTag）：
   ```
   db.transaction():
     if tag == "production":
       -- 先摘同项目其他版本的 production：
       -- 逐行读 metrics_snapshot_json，去掉 tags 中 "production" 后写回
       -- （tags 存 JSON 内，无法纯 SQL 更新，必须读-改-写；同事务保证唯一）
     给 versionId 追加 tag
   db.commit()；失败 rollback 并返回 false
   ```
   同项目定位：训练模型走 `run_id→training_runs.project_id`，导入模型走 `model_versions.project_id`（参照 ExportService.cpp:624-633 的双路 COALESCE 写法）。

3. **rollbackModel(versionId)**：把 production 挪回指定历史版本（内部同为 setTag 事务）；`AuditLog::record("model", versionId, "rolled_back", {from, to, reason})`；UI 弹窗要填回滚原因。
4. **UI**：ModelPage 晋级 / 回滚按钮 + ConfirmDialog（默认聚焦取消）；徽标区分 production / best / baseline；「已部署」提示若版本被回滚（v2.0 deploy_targets 联动本期只做提示文案）。

**测试用例**：

- T10-3 晋级无测试结论被拒。
- T12-1 晋级 / 回滚均落 task_events，含前后版本 id（test_audit_log 扩展）。

**验收命令**：`ctest --preset msvc2022-release -R "ModelTest|AuditLogTest" --output-on-failure`

**常见坑**：
- tags 在 JSON 里，「摘除其他 production」必须遍历同项目所有版本的 metrics_snapshot_json 读改写，漏一条就双 production；事务包住全程。

## 附录 C：队列项状态机

```text
                 ┌──→ reviewed（已标注/已回写，终态）
queued（入库）───┤
                 ├──→ discarded（拒绝，终态）
                 └──→ queued（保持，排序/优先级仅改 priority）
```

| 状态 | 含义 | 迁移入口 |
|------|------|----------|
| queued | 待处理 | 收集入库默认值 |
| reviewed | 已处理（标注确认/回写） | B2 确认后 |
| discarded | 已丢弃 | B2 拒绝 / 批量清理 |

统计口径：积压 = status='queued'；漏斗「已标注」= reviewed 中有 annotation_revisions 关联者；「已回写」= commit 成功计数；「已再训练」= task_events 事件 `retrain_from_batch` 计数。

## 附录 D：队列查询与漏斗 SQL

```sql
-- 分页列表（低置信队列，按优先级降序、置信度升序）
SELECT id, queue_type, sample_path, sample_id, dataset_id,
       reason, priority, confidence, class_index, class_name, status, created_at
FROM active_learning_items
WHERE queue_type = :queueType
  AND status = :status                      -- 通常 'queued'
  AND (:datasetId IS NULL OR dataset_id = :datasetId)
  AND (:className IS NULL OR class_name = :className)
ORDER BY priority DESC, confidence ASC
LIMIT :limit OFFSET :offset;

-- 筛选取值（下拉）
SELECT DISTINCT class_name FROM active_learning_items WHERE queue_type = :queueType LIMIT 200;

-- 各队列积压
SELECT queue_type, COUNT(*) FROM active_learning_items
WHERE status = 'queued' GROUP BY queue_type;

-- 漏斗：已收集
SELECT COUNT(*) FROM active_learning_items;
-- 漏斗：已标注 / 已回写（状态法）
SELECT SUM(CASE WHEN status='reviewed' THEN 1 ELSE 0 END) AS reviewed,
       SUM(CASE WHEN status='discarded' THEN 1 ELSE 0 END) AS discarded
FROM active_learning_items;
-- 漏斗：已再训练（事件法）
SELECT COUNT(*) FROM task_events WHERE event_type = 'retrain_from_batch';
```

索引：`idx_al_items_queue(queue_type, status)`（Schema.cpp:218）已覆盖主查询；如筛选卡顿再补 `(queue_type, status, priority)` 复合索引。
